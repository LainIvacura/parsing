# EGRUL/EGRIP Reload Watcher

Скрипт-наблюдатель, который сверяет данные организаций в БД с содержимым ZIP-архивов
из ЕГРЮЛ/ЕГРИП и автоматически запускает GitLab-пайплайн для перевыгрузки данных
по несовпадающим организациям.


## Проблема

Данные об организациях в ЕГРЮЛ/ЕГРИП периодически обновляются, и БД может
«отставать» от того, что лежит в архивах выгрузок. Расхождение видно глазами
(например, наименование в БД не совпадает с ФИО/названием в XML), но проверять
тысячи организаций вручную — нереально. Плюс если скрипт прерывался, он начинал
всё с нуля и повторно дёргал уже обработанные записи.

## Решение

Скрипт:

1. Читает из `oosIntegrationPacket` пакеты XML с типом `221` порциями по `BATCH_SIZE`.
2. Для каждой организации сравнивает `organization.fullName` из БД
   с ФИО/наименованием из XML, извлечённым прямо из ZIP-архива (без распаковки).
3. Накапливает несоответствия в буфер (`BATCH_MISMATCH_SIZE`).
4. При заполнении буфера запускает GitLab-пайплайн через API, передавая список
   ID организаций одним запросом.
5. Сохраняет «последний обработанный ID» в служебной таблице — при перезапуске
   продолжает с того же места.

Особенности:
- **Кэш проверенных организаций** (`checked_organizations`) — не проверяем одну
  и ту же организацию дважды за запуск.
- **Единая сессия SQLAlchemy** на весь цикл — меньше накладных расходов.
- **Пакетная обработка** — 1000 пакетов на итерацию с паузой между итерациями.
- **Синхронный httpx** — не требуется asyncio для последовательных вызовов API.
- **Остаток буфера** обрабатывается перед завершением, чтобы не потерять
  несоответствия на «хвосте».

## Результат

- Ручная сверка тысяч организаций → **полностью автоматическая проверка**
- Перевыгрузка запускается только по реально расходящимся организациям (не «всё подряд»)
- Устойчивость к перезапускам за счёт сохранения `last_processed_id`
- Прозрачный лог: видно, какая организация, какой ИНН, что было в БД, что в архиве

## Стек

- Python 3
- SQLAlchemy (через внутренний `ConnectionFactory`)
- `httpx` — запуск пайплайнов через GitLab API
- `xml.dom.minidom` + `zipfile` — чтение XML прямо из ZIP
- Работа с несколькими БД одновременно

## Запуск

```bash
git clone git@github.com:username/egrul-reload-watcher.git
cd egrul-reload-watcher
pip install -r requirements.txt

cp config.example.py config.py   # заполнить своими значениями

export GITLAB_API_URL=https://gitlab.example.com/api/v4
export GITLAB_PROJECT_ID=0000
export GITLAB_TRIGGER_TOKEN=glptt-xxxxxxxxxxxxxxxx
export GITLAB_BRANCH=main

python main.py
```

Скрипт завершается сам, когда новых пакетов для обработки нет.

## Настройки

### `config.py`

| Параметр | Назначение |
|---|---|
| `LOG_FILE` | Путь к лог-файлу |
| `RELOAD_SCRIPT_PATH` | Путь к PHP-скрипту перевыгрузки |
| `PACKETS_BASE_PATH` | Базовый путь XML-пакетов из БД |
| `ARCHIVES_BASE_PATH` | Базовый путь ZIP-архивов ЕГРЮЛ/ЕГРИП |

### Переменные окружения

| Переменная | Назначение |
|---|---|
| `GITLAB_API_URL` | Базовый URL GitLab API |
| `GITLAB_PROJECT_ID` | ID проекта в GitLab |
| `GITLAB_TRIGGER_TOKEN` | Pipeline trigger token (Settings → CI/CD → Pipeline triggers) |
| `GITLAB_BRANCH` | Ветка, в которой запускается пайплайн |

### Константы в `main.py`

| Параметр | Назначение |
|---|---|
| `DATE_FROM` / `DATE_TO` | Диапазон дат для выборки пакетов |
| `BATCH_SIZE` | Размер порции пакетов (по умолчанию 1000) |
| `BATCH_MISMATCH_SIZE` | Размер буфера несоответствий (по умолчанию 400) |
| `SLEEP_BETWEEN_ITERATIONS` | Пауза между итерациями в секундах |

## Примечания

- Использует внутреннюю библиотеку подключения к БД `support_citadel` — в репозитории
  заменена заглушкой.
- Реальные названия БД, пути и токен вынесены в `config.py` и переменные окружения,
  в репозиторий не попадают.
- GitLab-токен передаётся через переменные окружения и **не хранится в коде**.
- Скрипт рассчитан на запуск по расписанию (cron) в инфраструктуре сервиса.
